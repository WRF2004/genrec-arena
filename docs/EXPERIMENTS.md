# 从能运行到能讲清楚的实验路线

## 阶段一：验收闭环

运行 pytest 与 smoke.sh，查看真实记录 reports/。确认 loss 有下降、预测均合法、测试输入从未进入优化步骤、续训一致。合成数据有刻意构造的周期偏好，不具有业务代表性。

## 阶段二：H&M 子集基线

1. 按用户采样 1%，记录 SHA256、人数、商品数、冷商品比例、时间范围。
2. 相同输入跑 Popularity、ItemKNN、item-ID Transformer、SID 模型。
3. 先用验证集选择配置，之后一次性评测测试集。
4. 用 42、43、44 三个 seed 重跑神经模型；换 seed 需新 run 目录。
5. 记录 MAP@12 / Recall@12 / NDCG@12、覆盖率、延迟、参数量、训练时间。

不必强求 SID 胜出。若 ItemKNN 更强，检查购买窗口目标与单一下一商品训练目标不匹配、文本特征过弱、消歧后缀过长、数据稀疏、beam 过窄等原因。

## 阶段三：可以深入讨论的消融

| 实验 | 保持一致 | 判断什么 |
|---|---|---|
| random / residual K-Means / RQ-VAE | 相同数据、种子、网络 | 语义编码是否真正有效 |
| 哈希元数据 / 文本向量 / 图文拼接 | 相同划分与模型 | 内容表示的价值 |
| 码本 32/64/128，层数 2/3 | 其余训练预算 | 碰撞、压缩、长路径代价 |
| beam 12/32/64 | 固定 checkpoint | 质量与解码延迟 |
| history 10/30/50 | 每次重新训练 | 长历史收益与 token 成本 |

scripts/ablate.py 已自动化第一项，只输出验证集比较。其余通过修改配置复制成新实验，不覆盖旧文件。beam 测试可调用 `engine.predict` 对同一 checkpoint 解码；不要混淆重训随机性。

## 阶段四：统计与误差分析

```bash
python scripts/compare.py --a runs/hm-gen/test_predictions.json \
  --b runs/hm-seq/test_predictions.json --k 12 --metric MAP \
  --output runs/comparison.json
```

配对用户 bootstrap 报告差值与 95% 区间，只反映该数据切片的不确定性，不覆盖种子/划分偏差。工具要求相同用户与标签。

查看错误推荐：是否同类但不同商品？是否频繁物品占据前列？冷目标占比是否限制 Recall 上限？量化高碰撞桶是否导致退化？按用户历史长度、商品热度做额外分析时保持同一测试样本群。

## 面试讲解提纲

- 为什么不是把商品名称喂给通用 LLM？本项目直接学习结构化 ID 序列，生成空间可控、无需大模型权重。
- SID 是否有语义？看 random 对照与内容特征消融，不能仅凭聚类名字判断。
- 碰撞和坍缩有什么区别？多个商品相同完整语义码 vs 码本只使用少量中心；后缀解决前者唯一性，不能解决后者表示质量。
- 如何防泄漏？全局时间切分、训练目录、同日屏蔽、静态元数据、验证选模、测试不调参。
- 为什么不能直接说冷启动解决了？新商品不在冻结 Trie 中；内容编码能力不自动意味着系统支持新增商品。
- 为什么没直接用 PPO/GRPO？先建立可信的监督学习与离线评估基线，再考虑排序奖励；本项目未实现 RL，不在简历里声称有。
- 有何创新？当前是独立工程实现与受控实验平台，不声称提出新算法。真实研究点应由误差分析产生。

## 建议节奏

第 1–2 天理解并跑通；第 3–4 天真实子集与基线；第 5–7 天三种 tokenizer；第 8–10 天内容向量与 beam 延迟；第 11–14 天多 seed、置信区间、失败分析与项目报告。以实验结果决定是否扩展规模，不以模型名字堆叠功能。
